## 2026-06-11 — Platform Library upload: Celery asyncio loop crash in ingestion task
Status: fixed
Symptom:
  - celery-worker: RuntimeError — Future attached to a different loop
  - Ingestion task fails when calling run_db() for DB updates from prefork worker
Cause:
  - Celery prefork workers call asyncio.run() per task; reusing the API's module-level
    async engine/session factory binds connections to a closed event loop.
Fix:
  - api/app/db/celery_async.py — run_db() creates a disposable engine per call,
    disposes it before the loop closes
  - api/app/features/library/tasks.py imports run_db from celery_async (not session)
Verify:
  - celery-worker logs show book_status_updated / ingestion_complete (no RuntimeError)

## 2026-06-11 — Platform Library PDF upload: missing Compose profiles (minio / qdrant / workers)
Status: fixed
Symptom:
  - Upload may return 202 but ingestion never completes
  - celery-worker: Name or service not known (minio/infinity) OR no worker running
Cause:
  - Library upload needs: minio (file storage), qdrant (vectors), celery-worker (async ingest).
  - Services are behind Compose profiles: rag (minio, qdrant, infinity), workers (celery).
  - `docker compose up` alone starts only core (~7 containers) — no ingest pipeline.
Fix:
  - docker compose --profile rag --profile workers up
  - With EMBEDDING_PROVIDER=local (default), infinity is optional — still need minio + qdrant + worker
Verify:
  - docker compose ps shows minio, qdrant, celery-worker Up
  - Upload → status processing → available

## 2026-06-11 — Platform Library PDF upload: ingestion fails (Infinity not running)
Status: fixed
Symptom:
  - Upload POST /api/v1/admin/library/ → 202 Accepted; UI shows "ingesting"
  - Shortly after → status ingestion_failed on frontend
  - celery-worker: ingestion_failed error='[Errno -2] Name or service not known'
  - curl http://localhost:7997/health fails
Cause:
  - When EMBEDDING_PROVIDER=infinity, task embeds via INFINITY_URL (http://infinity:7997).
  - Infinity is behind Compose profile `rag`.
  - Stack was running with `workers` but without `rag`, or infinity never started.
  - Docker DNS cannot resolve hostname `infinity` when that container is absent.
Fix:
  - Dev default: EMBEDDING_PROVIDER=local in .env / docker-compose (embed in celery-worker)
  - OR start rag profile and wait: curl -f http://localhost:7997/health before upload
Verify:
  - Upload PDF → status processing → available (not ingestion_failed)
  - celery-worker logs: ingestion_complete

## 2026-06-11 — Platform Library PDF upload: Infinity crash-loop (exit 137 / OOM)
Status: fixed (mitigated; use local embedder on dev)
Symptom:
  - infinity-1 exited with code 137 (restarting) during/after upload
  - celery-worker: ingestion_failed error='[Errno 111] Connection refused'
  - Upload and pdf_extracted succeed; failure at embedding step only
Cause:
  - Infinity loads heavy ONNX models (BGE-M3 + bge-reranker-v2-m3) — ~2–4 GB RAM.
  - On 8 GB host with core + authentik + observability + all profiles, container
    is SIGKILL'd (137) while loading models.
  - Ingestion races the crash: Celery calls :7997 exactly when Infinity is down.
Fix:
  - Run lean stack: docker compose --profile rag --profile workers up
    (skip observability/events when not needed)
  - docker-compose.yml: removed reranker from infinity command (BGE-M3 only) to
    halve Infinity RAM for dev; mem_limit raised to 4g
  - Prefer EMBEDDING_PROVIDER=local so Infinity is not required locally
  - Increase Docker Desktop memory to 6–8 GB if using Infinity
Verify:
  - docker compose ps shows infinity Up (not restarting)
  - curl -f http://localhost:7997/health → OK before upload

## 2026-06-11 — Platform Library PDF upload: Infinity amd64 on Apple Silicon (Rosetta crash-loop)
Status: fixed
Symptom:
  - docker compose up infinity warns:
    "image's platform (linux/amd64) does not match host (linux/arm64/v8)"
  - curl http://localhost:7997/health → (56) Connection reset by peer
  - Infinity never reaches healthy; ingestion_failed Connection refused
Cause:
  - michaelf34/infinity:latest manifest is amd64-only (no arm64 tag on :latest).
  - Docker runs it under Rosetta emulation on M-series Mac — unstable, crash-loops
    during model load ("Waiting for application startup" then restart).
Fix:
  - docker-compose.yml: pin michaelf34/infinity:0.0.75 (multi-arch, includes arm64)
  - healthcheck start_period: 300s (first model download takes 2–5 min)
  - Dev workaround: EMBEDDING_PROVIDER=local — skip Infinity entirely on Mac
Verify:
  - docker image inspect michaelf34/infinity:0.0.75 --format '{{.Architecture}}' → arm64
  - curl -f http://localhost:7997/health succeeds after warm-up (if using Infinity)
